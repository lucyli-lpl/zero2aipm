# 模块 4 · 带着项目学方法论

## 为什么学这个

模块 3 之后，你手上有了时灵时不灵、偶尔做出奇怪事情的产品。这正是学方法论的最好时机。每个概念都有了落脚的地方："评测"不再是一个抽象的词，它就是你改完提示词后，判断 Agent 变好还是变差的办法。

这个模块里的方法，比工具变得慢得多。它们区分的是"做过 demo 的人"和"能把 AI 产品跑起来的人"。

## 怎么学：五天集中学习

想深入一个方向时，我会做一次五天集中学习，每天的结构固定：

- **精读 1 小时**，先写一份阅读地图：这篇讲什么、和我的项目有什么关系、重点读哪几部分。
- **拓展 2 小时**：相关的延伸阅读，或者把想法用到工作里。
- **一个动手任务**：产出一个能拿出来看的文件。
- **最后自测**：让 AI 出选择题、简答题和应用题，你答完它来批改。

跑下来有两条心得：通勤时间适合听播客，但别想着记笔记；大部分时候不需要报付费课，这个领域最好的作者，都把核心内容免费放出来了。

## 方法

### 1. 能力边界：决定 AI 在哪里该做、在哪里不该做

把产品里的每个场景放进三个区之一：

- **核心区**：AI 能稳定处理。这里测得最严，也是你承诺质量的地方。
- **边缘区**：在范围内，但 AI 有时做不好（知识不够、用户输入不清、流程有缺陷）。你要设计兜底，并持续改进。
- **界外区**：AI 不该尝试。正确的行为是转到别的模式、追问澄清、礼貌拒答，或者转人工。

这一张图，决定了你的测试方案、提示词规则和支持方案。

### 2. 评测：你怎么知道它变好了

- 建一组真实输入，每条写清期望的行为。开始时 20 到 50 条就够。
- 用通过/不通过判断，少用 1 到 10 分的打分。更快达成一致，也更好行动。
- 每次改提示词、知识或模型，前后都跑一遍整套评测。
- 评测集就是你的验收标准。在找人开发之前就写好。

### 3. 错误分析：让真实的失败告诉你修什么

- 收集真实的对话或运行轨迹，包括失败的。
- 逐条读，给每个失败写一句开放式的笔记。
- 把笔记归成几类（失败分类法），数每类有多少，先修最大的那类。
- "幻觉分数"这类通用指标，不如从你自己数据里长出来的分类有用。

### 4. 上下文工程：模型看到什么，就决定它做什么

- 按文档的形态选知识进入模型的方式。长篇文字适合检索（RAG）；结构化表格往往用结构化检索效果更好；少量稳定的规则可以直接放进系统提示词。
- 把稳定的全局规则（系统提示词）和只在特定场景按需加载的操作流程（skill）分开。
- 多用正面指令（"这样做"），少列一长串"不要做什么"。反例常常会渗进模型的行为里。
- 补充边界知识：产品覆盖什么、哪些品牌或部门、什么不在范围内。没有这些，模型在边缘处就会自由发挥。

### 5. Agent 和多 Agent：够用就好

从能用的最简单结构开始：先一次模型调用，再固定工作流，再 Agent。只有至少满足下面一条时，才考虑多 Agent：

- **上下文污染**：某个子任务会产生大量主任务用不上的信息。
- **并行探索**：任务需要同时朝很多方向搜索。
- **专业分工**：不同部分需要不同的工具或互相冲突的指令，或者一个 Agent 要背的工具太多。

同样的任务，多 Agent 系统消耗的 token 通常是单 Agent 的好几倍，总耗时也常常更长。

### 6. 从业务目标出发设计，而不是从架构出发

被要求设计一个 Agent 系统时（面试常考），按这个顺序来：

1. 业务目标。
2. 关键业务流程：人现在是怎么做的。
3. 哪里会出问题：代价最大的决策、延迟和错误在哪。
4. Agent 角色分工和人工介入点：哪些步骤需要人，为什么。
5. 怎么验证它有效：评测集和指标。

这样就把"搭一个 Agent"变成了"解决一个业务问题"，而后者才是面试官和业务方真正关心的。

## 练习

1. 从模块 3 的产品里挑你最在意的一个。
2. 和 AI 导师一起列出用户可能带来的 10 到 20 个场景，把每个放进一个区。存为 `my-journey/projects/<项目名>-boundaries.md`。
3. 把这些场景变成评测集（`templates/eval-set.csv`）：输入、期望行为、通过规则。
4. 用它跑一遍你的产品，诚实地记录结果。
5. 每个失败写一句哪里出了问题。让 AI 导师帮你归类，修掉最大的那一类，再跑一遍。
6. 做 AI 导师出的本模块测验。

## 自测

- 你产品里哪些场景属于界外区？产品是怎么处理它们的？
- 你的修复提升了整体评测结果，还是只修好了你盯着的那一个例子？
- 你的产品能不能更简单，用更少的 Agent 或更少的步骤，依然通过评测？

## 我的经历

那次五天集中学习里，我写了一套能力边界方法论，之后在工作中边用边改。一条诚实的心得：评测有写得很好的公开方法，但 AI 产品的数据运营（怎么定义 badcase、怎么设计打标、怎么把用户反馈接到修复上）当时还没有公认的经典文章。我把有来源的和自己推出来、待验证的假设分开标注。在没有教科书的领域，你自己的实践，就是方法论被写出来的方式。
